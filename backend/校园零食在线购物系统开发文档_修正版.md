## 2. 项目概述

### 2.1 项目背景
随着校园消费场景日益数字化，学生对零食、饮料、速食、糕点等商品的在线浏览、下单和购买需求不断增加。传统线下购买方式存在商品信息不透明、购买效率低、商品选择范围有限等问题。为提升校园零食购买体验，设计并实现一个基于 Spring Boot 与 Vue3 的校园零食在线购物系统具有较强的现实意义。

### 2.2 项目目标
本系统面向校园场景，构建一个具备完整购物流程的在线零食商城，实现以下核心目标：

1. 实现商品信息展示，包括图片、名称、价格、库存、描述、分类等。
2. 实现用户注册、登录、退出和个人信息维护。
3. 实现购物车功能，包括加入购物车、修改数量、删除商品、勾选结算、自动计算总价。
4. 实现订单生成功能，包括下单、订单明细记录、订单状态流转。
5. 实现后台管理功能，包括商品管理、分类管理、订单管理、公告管理、用户管理。
6. 采用前后端分离架构，前端使用 Vue3 + Vite，后端使用 Spring Boot，数据库使用 MySQL。

### 2.3 项目定位
本项目定位为中小型校园电商系统，主要服务对象为校内学生与管理员，适合用于毕业设计、课程设计与教学演示。

### 2.4 项目特色
- 场景明确：聚焦校园零食购买需求。
- 功能完整：覆盖用户、商品、购物车、订单、后台管理等典型模块。
- 架构清晰：采用前后端分离开发模式。
- 技术主流：使用 Vue3、Spring Boot、MySQL 等常见技术。
- 易于扩展：后续可扩展支付、优惠券、秒杀、评价、推荐等功能。

## 4. 系统架构设计

### 4.1 总体架构
系统采用前后端分离架构：

1. 前端负责页面展示、用户交互、表单校验、状态管理和接口调用。
2. 后端负责业务逻辑处理、身份认证、权限控制、数据持久化和接口输出。
3. 数据库负责用户、商品、购物车、订单等业务数据存储。

### 4.2 架构图说明
- 用户通过浏览器访问前端 Vue3 项目；
- 前端通过 Axios 请求 Spring Boot 提供的 RESTful API；
- 后端接收请求后进行参数校验、业务处理和数据库操作；
- 最终将统一 JSON 结果返回前端。

## 5. 功能需求分析

### 5.1 用户端功能

#### 5.1.1 用户注册
用户输入用户名、密码、手机号等信息完成注册，系统验证用户名唯一性和基本格式合法性。

**【修正】校验规则：**
- 用户名：4~20位，仅允许字母、数字、下划线
- 密码：6~20位，不得为纯数字
- 手机号：符合中国大陆手机号格式（可选填）

#### 5.1.2 用户登录
用户通过账号密码登录，后端校验成功后返回 token，前端保存并用于后续请求认证。

#### 5.1.3 商品浏览
用户可在首页或商品列表页查看零食商品信息，包括商品图片、名称、价格、销量、库存和简要描述。**【修正】前端仅展示状态为上架（status=1）的商品。**

#### 5.1.4 商品分类与搜索
用户可按分类浏览商品，也可通过关键词搜索商品。

#### 5.1.5 商品详情
用户点击商品后可进入详情页，查看更详细的商品介绍、库存情况、规格说明等。**【修正】若商品已下架，详情页应给出提示，不允许加入购物车。**

#### 5.1.6 购物车
用户可将商品加入购物车，对购物车中的商品进行增减数量、删除、勾选结算、清空等操作。**【修正】展示购物车时，若购物车内商品已下架，应标记为"已下架"并在结算时自动跳过，不得计入总价。**

#### 5.1.7 提交订单
用户选择购物车商品，填写或从收货地址簿中选取收货信息后生成订单。

#### 5.1.8 我的订单
用户可查看订单列表、订单详情、取消订单、确认收货等。

#### 5.1.9 个人中心
用户可查看与修改昵称、手机号、头像等信息，并管理收货地址。

**【修正】收货地址管理为独立功能，包含：**
- 新增收货地址
- 修改收货地址
- 删除收货地址
- 设为默认地址
- 下单时选择已保存地址或临时填写

### 5.2 管理端功能

#### 5.2.1 商品管理
管理员可新增、修改、删除、上下架商品，维护商品图片、名称、价格、库存和描述。**【修正】删除商品前应检查是否存在关联的未完成订单，若有则禁止删除或仅做软删除（is_deleted=1）。**

#### 5.2.2 分类管理
管理员可对商品分类进行新增、编辑、删除、排序。**【修正】删除分类前需检查分类下是否有商品，若有则禁止删除并提示。**

#### 5.2.3 订单管理
管理员可查看订单列表、订单详情，按合法状态流转修改订单状态。**【修正】详见第8节订单状态机设计。**

#### 5.2.4 用户管理
管理员可查询用户列表、查看用户资料、禁用或启用用户。

#### 5.2.5 公告管理
管理员可发布和维护首页公告，展示促销、通知等内容。

#### 5.2.6 统计分析
管理员可查看商品数量、订单数量、销售金额、热销商品等统计信息。

## 6. 非功能需求

### 6.1 性能需求
- 商品列表分页查询响应时间尽量控制在 2 秒以内。
- 常规接口响应时间尽量控制在 1 秒以内。
- 支持不少于 100 人的基础并发访问演示。

**【修正】为支持该并发目标，需配置以下内容：**
- 数据库连接池：使用 HikariCP，`maximum-pool-size` 建议配置为 20~30
- 高频查询字段（如 `user_id`、`category_id`）需建立索引（详见数据库设计）

### 6.2 安全需求
- 用户密码必须使用 **BCrypt** 算法加密存储，**【修正】禁止使用 MD5 或 SHA256 直接存储密码**。
- 登录后访问受保护接口必须携带 JWT token。
- **【修正】token 建议存储在内存（Pinia store）中，不建议使用 localStorage（存在 XSS 窃取风险）。若使用 localStorage，需确保接口内容不含敏感操作的自动触发，并在生产环境启用 CSP 防护。**
- 关键业务接口需进行参数校验（使用 `@Valid` + `BindingResult` 或全局异常捕获）。
- 后台管理接口需进行角色权限控制，从 JWT Claims 中读取 `role` 字段，在拦截器中验证。
- **【修正】所有涉及用户资源的接口（订单、购物车）必须在 Service 层校验资源归属，即当前 token 用户与资源 user_id 是否一致，防止越权访问（IDOR 攻击）。**

### 6.3 可维护性需求
- 代码分层清晰，遵循 Controller、Service、Mapper、Entity 的层次。
- 接口返回格式统一。
- 数据库表命名规范统一。
- 文档描述清晰，便于后期维护。

### 6.4 可扩展性需求
系统应保留以下扩展能力：
- 支付功能
- 商品评价功能
- 优惠券功能
- 推荐算法
- 秒杀活动
- 消息通知

### 7.4 SQL 建表脚本

```sql
CREATE DATABASE IF NOT EXISTS campus_snack_mall
DEFAULT CHARACTER SET utf8mb4
DEFAULT COLLATE utf8mb4_unicode_ci;

USE campus_snack_mall;

CREATE TABLE sys_user (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    username    VARCHAR(50)  NOT NULL COMMENT '用户名',
    password    VARCHAR(255) NOT NULL COMMENT 'BCrypt加密密码',
    nickname    VARCHAR(50)           COMMENT '昵称',
    phone       VARCHAR(20)           COMMENT '手机号',
    avatar      VARCHAR(500)          COMMENT '头像相对路径',
    role        VARCHAR(20)  NOT NULL DEFAULT 'USER' COMMENT 'USER/ADMIN',
    status      TINYINT      NOT NULL DEFAULT 1 COMMENT '1正常 0禁用',
    create_time DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_username (username)
) COMMENT='用户表';

CREATE TABLE sys_user_address (
    id               BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id          BIGINT      NOT NULL COMMENT '用户ID',
    receiver_name    VARCHAR(50) NOT NULL COMMENT '收货人',
    receiver_phone   VARCHAR(20) NOT NULL COMMENT '联系电话',
    receiver_address VARCHAR(255) NOT NULL COMMENT '详细地址',
```

## 8. 后端设计说明

### 8.1 包结构设计【修正：统一采用传统三层结构，不再双轨并行】

```text
com.campus.snackmall
├─ CampusSnackMallApplication
├─ common
│  ├─ api              # 统一返回结构 Result<T>、状态码枚举
│  ├─ config           # 跨域配置、拦截器注册、文件上传配置
│  ├─ exception        # 全局异常处理器、自定义业务异常
│  └─ util             # JWT 工具类、文件工具类、雪花ID生成器
├─ controller          # 所有 Controller，按模块分子包
├─ service
│  └─ impl
├─ mapper
├─ entity              # 数据库实体类
├─ dto                 # 接收前端请求的 DTO
└─ vo                  # 返回给前端的 VO
```

### 8.2 分层说明

#### Controller 层
- 接收请求参数（使用 DTO 接收，加 `@Valid` 注解）
- 从 token 中解析当前用户 ID，传入 Service
- 调用 Service
- 返回统一结果 `Result<T>`

#### Service 层
- 编写业务逻辑
- **【修正】涉及用户资源操作时，必须校验资源归属（当前用户 ID 是否与记录的 user_id 一致）**
- 校验库存、用户状态、订单状态等

#### Mapper 层
- 负责与数据库交互
- 完成增删改查

#### Entity / DO
- 与数据库表字段映射，使用 MyBatis Plus 注解

#### DTO / VO
- DTO 用于接收请求，加 JSR-303 校验注解
- VO 用于返回前端展示数据，只暴露必要字段

### 8.3 统一返回格式
所有接口统一如下格式：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {}
}
```

**【修正】业务错误码规范：**

| code | 含义 |
|---|---|
| 200 | 成功 |
| 400 | 参数错误（校验失败） |
| 401 | 未登录或 token 失效 |
| 403 | 无权限（含越权访问） |
| 404 | 资源不存在 |
| 409 | 业务冲突（如库存不足、用户名已存在） |
| 500 | 服务器内部异常 |

**【修正】库存不足应返回 code=409，不得使用 500。**

### 8.4 鉴权方案【修正：补充完整说明】

采用 JWT 鉴权：

1. 用户登录成功后，后端生成 JWT token，Payload 中包含 `userId`、`role`、`exp`（过期时间）。
2. 前端将 token 存入 Pinia store（内存），页面刷新后需重新登录，或结合 `sessionStorage` 持久化（不推荐 localStorage）。
3. 后续请求在请求头中携带：`Authorization: Bearer <token>`
4. 后端拦截器解析 token，将 `userId` 和 `role` 注入请求上下文（ThreadLocal），供 Service 层使用。
5. 管理员接口拦截器额外校验 `role == ADMIN`，否则返回 403。
6. **【修正】token 中的 role 决定权限，但 Service 层仍需从数据库读取用户状态，若用户已被禁用（status=0）则拒绝请求，返回 401。**

### 8.5 订单状态机设计【修正：明确状态流转规则，禁止非法流转】

**状态定义（tinyint 存储）：**

| 值 | 状态常量 | 说明 |
|---|---|---|
| 1 | CREATED | 已创建（待处理） |
| 2 | DELIVERING | 配送中 |
| 3 | FINISHED | 已完成 |
| 4 | CANCELLED | 已取消 |

**合法状态流转矩阵：**

| 当前状态 | 可流转到 | 操作方 |
|---|---|---|
| CREATED(1) | DELIVERING(2) | 管理员 |
| CREATED(1) | CANCELLED(4) | 用户 / 管理员 |
| DELIVERING(2) | FINISHED(3) | 用户（确认收货）/ 管理员 |
| DELIVERING(2) | CANCELLED(4) | 管理员 |
| FINISHED(3) | — | 终态，不可流转 |
| CANCELLED(4) | — | 终态，不可流转 |

**【修正】Service 层必须按此矩阵校验，非法流转应抛出业务异常，返回 code=409。**

### 8.6 关键业务逻辑

#### 8.6.1 加入购物车逻辑
1. 验证用户已登录
2. 校验商品是否存在且为上架状态（`is_deleted=0 AND status=1`）
3. 校验添加数量 > 0
4. 使用 `INSERT INTO ... ON DUPLICATE KEY UPDATE quantity = quantity + ?` 原子操作，利用 `(user_id, product_id)` 唯一索引防并发重复插入

#### 8.6.2 提交订单逻辑（关键：原子性与价格快照）
1. 获取用户勾选的购物车商品（`checked=1`，且商品上架）
2. 校验购物车不为空
3. **【修正】从数据库重新读取商品当前价格，而非直接信任购物车中的价格，防止价格篡改**
4. 使用乐观锁扣减库存：`UPDATE snack_product SET stock = stock - ?, version = version + 1 WHERE id = ? AND version = ? AND stock >= ?`，若更新行数为 0 则表示库存不足或并发冲突，返回 409
5. **【修正】使用服务端计算的金额写入 `snack_order.total_amount`，`snack_order_item.price` 记录下单时快照价格，`amount = price × quantity`**
6. 同步更新商品销量：`UPDATE snack_product SET sales = sales + ? WHERE id = ?`
7. 生成唯一订单编号（推荐：雪花算法 或 时间戳+随机数）
8. 清理已下单的购物车记录
9. 上述步骤在同一事务（`@Transactional`）中执行，任一步骤失败则全部回滚

#### 8.6.3 取消订单逻辑【修正：明确库存恢复策略】
1. 校验订单存在且属于当前用户（或管理员）
2. 校验当前状态为 `CREATED(1)` 或 `DELIVERING(2)`（管理员可取消配送中订单，用户只能取消 CREATED 状态订单）
3. 将订单状态更新为 `CANCELLED(4)`
4. **【修正】取消后必须恢复库存**：`UPDATE snack_product SET stock = stock + ? WHERE id = ?`，并同步减少 `sales`
5. 以上步骤在同一事务中执行

#### 8.6.4 购物车归属校验【新增】
- `PUT /api/cart/{id}` 和 `DELETE /api/cart/{id}` 操作前，Service 层必须查询该购物车记录的 `user_id` 并与 token 中的 `userId` 比对，不一致则返回 403。

## 16. 风险与注意事项

### 16.1 已知风险与对应措施

| 风险 | 规避措施 |
|---|---|
| 库存超卖 | 乐观锁 + `CHECK (stock >= 0)` 约束双重保障 |
| 越权访问订单/购物车 | Service 层强制校验资源归属 |
| 价格篡改 | 下单时服务端重新查询价格，订单明细记录快照 |
| 订单状态非法流转 | 服务端状态机校验，拒绝非法流转 |
| 销量数据不一致 | 下单和取消均在同一事务内同步更新 sales 字段 |
| 前后端字段命名不一致 | 联调前固定接口 VO 字段，使用接口文档约束 |
| token 安全 | 存储于内存/sessionStorage，配合 CSP 降低 XSS 风险 |
| 图片 URL 部署失效 | 数据库存相对路径，URL 前缀由配置文件管理 |
| 数据库密码泄露 | 配置文件使用环境变量，禁止明文写死密码 |
